IBus Stage 0 Diagnostics Implementation Plan

Status: Connection-only diagnostics implemented and validated on 2026-08-10; the transient-registration lifecycle gate failed live validation and the broader Stage 0 roadmap remains in progress. Stage 1 is not approved by this plan.

This is a living plan. Later edits append to Amendments and do not rewrite prior amendment entries.

Outcome and boundaries

Provide a bounded diagnostic that determines whether the user's distro Python can reach PyGObject, the IBus typelib, the graphical session bus, and the running IBus bus. Component registration was removed after its live lifecycle check changed the selected IBus engine.

Stage 0 never registers a component or engine, commits or preedits text, reads surrounding text, changes the global engine/input source, starts an IBus daemon, installs system packages, or changes the default insertion backend.

Architecture and data flow

lst-ibus-check
      |
      v
project Python controller
  - validates timeout and executable
  - removes project Python overlays
  - starts distro Python with -I over private pipes
      |
      v
distro Python child
  - import GI and IBus typelib
  - connect to session D-Bus and IBus
  - destroy IBus bus and emit one bounded v1 JSON result
      |
      v
human or JSON diagnostic; exit 0 only when requested checks are ready

The child is a one-shot probe rather than a service, so Stage 0 needs no Unix socket or D-Bus protocol of its own. The parent accepts only a fixed, versioned result schema and reports child failures by stage/type without raw stderr or exception text.

Implementation steps

DONE 1. Define the non-mutating result contract.

Use a fixed schema with capability booleans, bounded failure stage/type, readiness and actions. A compatibility request for the removed registration experiment refuses before interpreter resolution or child execution.

Done when malformed, oversized or mode-mismatched child output fails closed without exposing raw errors.
DONE 2. Isolate the system-Python probe.

Resolve the distro interpreter, invoke it with -I, strip virtualenv/Python overlays, retain graphical-session variables, and enforce a 0.1–30 second total subprocess timeout.

Done when missing Python/GI/typelib/buses and child timeout each produce a stable action without starting IBus.
FAILED GATE 3. Reject transient registration.

The empty-component experiment returned success and clean shutdown but changed the selected engine from xkb:us::eng to vocalinux. The CLI option and all child registration code were removed; compatibility API requests fail before starting a child.

Gate remains failed unless a future independently approved design can prove zero input-source change. Stage 0 does not attempt restoration because that would itself manipulate the global engine.
DONE 4. Add launcher, installer and documentation.

Install lst-ibus-check with the general uv profile and document its no-insertion/no-input-source guarantee.

Done when checkout and packaged-root launchers support --help without side effects and installer tests include the launcher.
IN PROGRESS 5. Validate automation and the live session.

Hermetic and live connection-only checks pass. The registration lifecycle experiment failed the no-input-source-change condition and is no longer an accepted validation command.

Connection diagnostics are complete. The original lifecycle portion remains a failed gate, not evidence supporting Stage 1.

Failure and privacy rules

  • Raw child stderr and exception messages never enter JSON or human output.
  • Timeout kills the isolated child through the bounded subprocess runner.
  • No transcript, window metadata, repository path or input-source value is collected.
  • A successful Stage 0 result proves connection capability only; it does not prove registration lifecycle or text delivery.
  • Stage 1 stays gated by real P1 metrics and Vocalinux interoperability.

Open decisions

Connection-only diagnostics need no further design decision. Transient registration remains rejected by a failed live gate. Whether to revisit that gate or build Stage 1 requires separate approval and remains conditional on measured daily insertion failures and the upstream interoperability decision.
